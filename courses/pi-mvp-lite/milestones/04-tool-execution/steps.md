## Step 4.1: Define the tool call type

**Goal:** Add a `ToolCallBlock` type to `src/types.ts` so assistant messages can contain tool call requests.

### Why This Step Exists

In Milestone 2, assistant messages only contained text (`TextContent[]`). But real LLM responses can contain both text ("Let me read that file for you") *and* structured tool calls ("I'll call `read_file` with path='README.md'"). You need a new content block type to represent those tool calls.

The `ToolCallBlock` joins `TextContent` in the assistant's `content` array, making it `(TextContent | ToolCallBlock)[]`. This lets a single message contain both explanatory text and one or more tool calls.

### Requirements

Add this interface to `src/types.ts`:

```typescript
export interface ToolCallBlock {
  type: "toolCall";                          // discriminant — distinguishes from TextContent (type: "text")
  id: string;                                // unique identifier for this specific call
  name: string;                              // which tool to call (e.g., "read_file")
  arguments: Record<string, unknown>;        // the arguments the LLM wants to pass
}
```

Then update `AssistantMessage` to accept tool call blocks alongside text:

```typescript
export interface AssistantMessage {
  role: "assistant";
  content: (TextContent | ToolCallBlock)[];  // ← changed from TextContent[]
  model: string;
  provider: string;
  stopReason: "stop" | "toolCalls" | "error" | "aborted";
  errorMessage?: string;
  timestamp: number;
}
```

**Why `id: string`?** Each tool call gets a unique ID (generated by your code or the mock). When you execute the tool and create a result, you include this same ID in the `ToolResultMessage`. The LLM uses the ID to match results back to their calls.

**Why `arguments: Record<string, unknown>`?** Tool arguments come as JSON from the LLM — generic key-value pairs. Using `unknown` (not `any`) forces you to validate before using them. You'll add validation in Step 4.5.

**Why the content change affects existing code:** Any code that accesses `message.content` and assumes all items are `TextContent` will need a type check. That's why the detection helpers in Step 4.4 use `.filter(c => c.type === "toolCall")` — they narrow the union to just `ToolCallBlock`.

### ??? warning "Breaking Change"

Changing `content: TextContent[]` to `content: (TextContent | ToolCallBlock)[]` is a breaking change to the `AssistantMessage` type. Any existing code that accesses `content[i].text` directly will now get a TypeScript error because the item might be a `ToolCallBlock` instead. You'll fix this by adding type guards wherever you access content blocks.

- [ ] `AssistantMessage.content` is `(TextContent | ToolCallBlock)[]`
- [ ] Running `npm run build` compiles — you may need to fix a few type errors in `loop.ts` from the content change

## Step 4.2: Update the Tool interface with requiredFields

**Goal:** Add a `requiredFields` property to the `Tool` interface so your validation code knows which arguments to check.

### Why This Step Exists

Before executing any tool, you need to verify that the LLM provided all required arguments. The `read_file` tool needs a `path` — without it, `fs.readFile(undefined)` crashes. By declaring required fields on each tool, your validation function can check them generically without knowing about each tool's specific requirements.

This is simpler than the full course's Zod schema approach but serves the same purpose: prevent crashes from missing inputs.

### Requirements

Update the `Tool` interface in `src/types.ts`:

```typescript
export interface Tool {
  name: string;
  description: string;
  requiredFields: string[];              // ← NEW: list of argument names that must be present
  execute(
    toolCallId: string,
    args: Record<string, unknown>,
  ): Promise<ToolResult>;
}
```

**Why `string[]` and not a more complex schema?** For an MVP, knowing which fields are required is enough. The full course uses Zod schemas that also validate types (e.g., "path must be a string") and constraints (e.g., "port must be between 1 and 65535"). A simple array of field names handles the common case.

## Step 4.3: Add tool registration to the Agent class

**Goal:** Give the Agent a `registerTool()` method so tools can be added at runtime.

### Why This Step Exists

Tools aren't hardcoded into the agent — they're registered dynamically. This means you can have different agents with different capabilities (one with file reading, one with web searching, etc.) using the same Agent class. The `registerTool()` method is how you add capabilities.

### Requirements

Add this method to the `Agent` class in `src/agent.ts`:

```typescript
registerTool(tool: Tool): void {
  this._state.tools.push(tool);
}
```

**Why push instead of replace?** `push` adds to the existing array, so you can register multiple tools: `agent.registerTool(readFileTool); agent.registerTool(webSearchTool);`. The full course uses a `Map<string, Tool>` keyed by name for O(1) lookups — but with few tools, an array with `.find()` is simpler and fast enough.

**Why not accept tools only in the constructor?** Runtime registration lets you add tools conditionally (e.g., only register `web_search` if the user has a search API key). It also makes testing easier — you can create an agent with no tools and add them as needed.

## Step 4.4: Implement tool call detection helpers

**Goal:** Add utility functions in `src/loop.ts` that find and extract tool calls from assistant messages.

### Why This Step Exists

After the LLM responds, you need to know: "Did it call any tools?" The answer lives in the message's `content` array — some blocks are `TextContent` (just text) and some are `ToolCallBlock` (tool requests). These helpers separate the concerns of *detecting* tool calls from *executing* them.

### Requirements

Add these functions to `src/loop.ts`:

```typescript
/** Check if any content block in the message is a tool call */
export function hasToolCalls(message: AssistantMessage): boolean {
  return message.content.some((c) => c.type === "toolCall");
}

/** Extract all tool call blocks from the message */
export function getToolCalls(message: AssistantMessage): ToolCallBlock[] {
  return message.content.filter(
    (c): c is ToolCallBlock => c.type === "toolCall",
  );
}

/** Create a ToolResultMessage from a tool execution result */
export function createToolResultMessage(
  result: ToolResult,
  toolCall: ToolCallBlock,
): ToolResultMessage {
  return {
    role: "toolResult",
    toolCallId: toolCall.id,
    toolName: toolCall.name,
    content: result.content,
    isError: result.isError,
    timestamp: Date.now(),
  };
}
```

**Why `(c): c is ToolCallBlock` in the filter?** This is a TypeScript *type predicate* — it tells the compiler that after filtering, every element is a `ToolCallBlock`. Without it, the return type would be `(TextContent | ToolCallBlock)[]` and you'd need casts everywhere.

**Why separate `hasToolCalls` and `getToolCalls`?** You check `hasToolCalls()` first as a cheap boolean check (`.some()` stops at the first match). Only if true do you call `getToolCalls()` (`.filter()` scans the entire array). This avoids unnecessary work when most messages are text-only.

- [ ] All three helper functions exist and are exported
- [ ] `hasToolCalls` returns `true` for messages with tool call blocks

## Step 4.5: Implement argument validation

**Goal:** Add a function in `src/loop.ts` that validates tool arguments before execution.

### Why This Step Exists

The LLM generates tool arguments as JSON — it might forget a required field, pass the wrong type, or include extra fields. If you pass invalid arguments directly to a tool's `execute()` function, it crashes with an unhelpful error ("Cannot read property of undefined"). Validation catches these problems *before* execution and returns clear error messages that the LLM can understand and fix.

### Requirements

Add this function to `src/loop.ts`:

```typescript
/**
 * Validate that all required fields are present in the arguments.
 * Returns true if valid, or an error message string if invalid.
 */
export function validateToolArguments(
  toolName: string,
  args: Record<string, unknown>,
  requiredFields: string[],
): true | string {
  for (const field of requiredFields) {
    if (!(field in args)) {
      return `Tool '${toolName}' is missing required field: '${field}'`;
    }
    if (args[field] === undefined || args[field] === null) {
      return `Tool '${toolName}' has null/undefined value for field: '${field}'`;
    }
  }
  return true;
}
```

**Why return `true | string` instead of throwing?** The calling code can handle the error gracefully: if validation fails, create an error `ToolResultMessage` and feed it back to the LLM. The LLM sees the error ("missing field: path") and can retry with correct arguments. Throwing would require try/catch and crash the loop if not handled.

**Why check both `!(field in args)` and `args[field] === null`?** A field could be present but set to `null` or `undefined`. Both cases mean "the argument wasn't provided." Checking both catches more errors than just checking presence.

### ✅ Quick Checkpoint

- [ ] `validateToolArguments` exists and returns `true` for valid args
- [ ] It returns an error string when a required field is missing

## Step 4.6: Implement tool execution with error handling

**Goal:** Add a function in `src/loop.ts` that executes a single tool call and handles errors gracefully.

### Why This Step Exists

Tool execution is where your code actually *does* something — reads a file, runs a command, queries a database. But tools can fail: the file might not exist, the command might hang, the network might time out. Your execution function must catch these errors and convert them into `ToolResult` objects with `isError: true`, so the loop continues instead of crashing.

### Requirements

Add this function to `src/loop.ts`:

```typescript
/**
 * Execute a single tool call. Catches all errors and returns them as ToolResult with isError: true.
 */
async function executeToolCall(
  toolCall: ToolCallBlock,
  tool: Tool,
  args: Record<string, unknown>,
): Promise<ToolResult> {
  try {
    return await tool.execute(toolCall.id, args);
  } catch (error) {
    const message = error instanceof Error ? error.message : String(error);
    return {
      content: [
        { type: "text", text: `Error executing '${tool.name}': ${message}` },
      ],
      isError: true,
    };
  }
}
```

**Why the try/catch wraps the entire execute call?** Any error inside the tool — file not found, permission denied, network timeout — is caught and converted to a structured error result. The LLM sees `"Error executing 'read_file': ENOENT: no such file"` and can adapt (suggest a different path, ask the user, etc.).

**Why not rethrow errors from tools?** If a tool throws and isn't caught, the entire agent loop crashes. By always returning a `ToolResult` (success or error), the loop stays in control and decides what to do next.

### ✅ Quick Checkpoint

- [ ] `executeToolCall` exists and wraps `tool.execute()` in try/catch
- [ ] Caught errors return `{ isError: true }` with a descriptive message
- [ ] Running `npm run build` compiles without errors

## Step 4.7: Wire tools into the loop

**Goal:** Update `runLoop` in `src/loop.ts` to detect tool calls, execute them, and continue looping until the LLM gives a final answer.

### Why This Step Exists

This is the key structural change: your loop now has an **inner loop**. After getting an LLM response, instead of immediately checking "are we done?", it first checks "did the LLM call any tools?" If yes, it runs them, adds results to context, and loops back for another LLM call. This is the "act → observe → reason again" cycle that makes agents iterative.

### Requirements

Update the `while(true)` loop in `runLoop`. After getting the assistant message and emitting message events, add a tool execution branch:

```typescript
// ... after getting assistantMessage and emitting message_start/message_update/message_end ...

// Check if the LLM wants to call tools
if (hasToolCalls(assistantMessage)) {
  const toolCalls = getToolCalls(assistantMessage);

  for (const toolCall of toolCalls) {
    // Find the registered tool by name
    const tool = config.tools.find((t) => t.name === toolCall.name);

    if (!tool) {
      // Unknown tool — create an error result so the LLM knows
      const errorResult: ToolResult = {
        content: [{ type: "text", text: `Unknown tool: '${toolCall.name}'` }],
        isError: true,
      };
      const resultMsg = createToolResultMessage(errorResult, toolCall);
      messages.push(resultMsg);
      onEvent({ type: "message_start", message: resultMsg });
      onEvent({ type: "message_end", message: resultMsg });
      continue; // try next tool call
    }

    // Validate arguments
    const validation = validateToolArguments(
      tool.name,
      toolCall.arguments,
      tool.requiredFields,
    );

    if (validation !== true) {
      // Validation failed — return error to LLM so it can retry
      const errorResult: ToolResult = {
        content: [{ type: "text", text: validation }],
        isError: true,
      };
      const resultMsg = createToolResultMessage(errorResult, toolCall);
      messages.push(resultMsg);
      onEvent({ type: "message_start", message: resultMsg });
      onEvent({ type: "message_end", message: resultMsg });
      continue; // try next tool call
    }

    // Execute the tool
    const result = await executeToolCall(toolCall, tool, toolCall.arguments);
    const resultMsg = createToolResultMessage(result, toolCall);
    messages.push(resultMsg);
    onEvent({ type: "message_start", message: resultMsg });
    onEvent({ type: "message_end", message: resultMsg });
  }

  // All tools executed — loop back to call LLM again with results
  onEvent({ type: "turn_end", message: assistantMessage });
  continue; // ← inner loop: call LLM again
}

// No tool calls — the LLM gave a final answer
onEvent({ type: "turn_end", message: assistantMessage });

// Check if we should stop
if (shouldStopAfterTurn?.(assistantMessage) ?? true) {
  break;
}
```

**Why `continue` after tool execution?** After running all tools and adding their results to the conversation, the loop goes back to the top (`while(true)`) and calls the LLM again. The LLM now sees the tool results in context and decides what to do next — call another tool, or give a final answer.

**Why check for unknown tools?** The LLM might request a tool that wasn't registered (e.g., if the tool list sent to the API is out of sync with registered tools). Instead of crashing, you return a clear error: `"Unknown tool: 'web_search'"`. The LLM sees this and can try a different approach.

**Why validate before execute?** If arguments are missing, the tool would crash with a runtime error. Validation catches this early and returns a structured error that the LLM can understand ("missing field: path") instead of a stack trace.

### ??? warning "The Loop Must Terminate"

The `while(true)` loop will run forever if the LLM keeps calling tools indefinitely. In production, you add a **max turns limit** (e.g., stop after 10 tool calls). For this milestone, the mock LLM always returns `stopReason: "stop"` so it exits after one turn. When you add real LLM calls in Milestone 5, consider adding a turn counter:

```typescript
let maxTurns = 10;
while (maxTurns-- > 0) {
  // ... loop body ...
}
// After the loop: if maxTurns <= 0, emit an error event about hitting the limit
```

## Step 4.8: Create a `read_file` tool

**Goal:** Build a concrete, working tool that reads files from disk — so you can test the full pipeline end-to-end.

### Why This Step Exists

You've built all the infrastructure (types, detection, validation, execution). Now you need an actual tool to prove it works. The `read_file` tool is the simplest useful tool — it takes a path, reads the file, and returns the content. If this works, any tool can work.

### Requirements

Create a new file `src/tools/read-file.ts`:

```typescript
import fs from "fs/promises";
import type { Tool, ToolResult } from "../types.js";

export const readFileTool: Tool = {
  name: "read_file",
  description:
    "Read the contents of a file at the given path. Returns the file content as text.",
  requiredFields: ["path"],
  execute: async (_toolCallId, args): Promise<ToolResult> => {
    const path = args.path as string;

    try {
      const content = await fs.readFile(path, "utf-8");
      return {
        content: [{ type: "text", text: content }],
        isError: false,
      };
    } catch (error) {
      const message = error instanceof Error ? error.message : String(error);
      return {
        content: [{ type: "text", text: `Failed to read file at '${path}': ${message}` }],
        isError: true,
      };
    }
  },
};
```

**Why `fs/promises` instead of `fs`?** The promises API (`fs/promises`) returns a `Promise` that you can `await`. The callback API (`fs.readFile(path, callback)`) requires callbacks. Since `execute` is `async`, the promises API fits naturally.

**Why cast `args.path as string`?** Tool arguments are `Record<string, unknown>`, so TypeScript doesn't know `args.path` is a string. You validated it exists (Step 4.5), and for this MVP you trust the LLM provided a string. The full course uses Zod to validate types too.

**Why the description mentions what it returns?** The LLM reads the description to decide when to use the tool. A good description tells the LLM: what the tool does, what arguments it needs, and what format the output is in. This helps the model generate correct arguments and interpret results.

```typescript
import { Agent } from "./agent.js";
import { readFileTool } from "./tools/read-file.js";
import type { AgentEvent } from "./types.js";

async function main() {
  try {
    const config = loadConfig();

    const agent = new Agent({
      systemPrompt: config.systemPrompt,
      model: config.model,
    });

    // Register the read_file tool
    agent.registerTool(readFileTool);
    console.log("Registered tools:", agent.state.tools.map((t) => t.name).join(", "));

    // Event logger (add tool result handling)
    const onEvent = (event: AgentEvent) => {
      switch (event.type) {
        case "agent_start":
          console.log("\n[Agent started]");
          break;
        case "turn_start":
          console.log("  [Turn started]");
          break;
        case "message_start": {
          if (event.message.role === "toolResult") {
            const toolMsg = event.message;
            console.log(`    [Tool result: ${toolMsg.toolName} - ${(toolMsg as any).isError ? "ERROR" : "OK"}]`);
          } else {
            console.log("    [Message generation started]");
          }
          break;
        }
        case "message_update":
        case "message_end": {
          const text = event.message.content
            .map((c) => (c.type === "text" ? c.text : `[tool call: ${(c as any).name}]`))
            .join("");
          console.log(`    ${text}`);
          break;
        }
        case "turn_end":
          console.log("  [Turn ended]");
          break;
        case "agent_end":
          console.log(`[Agent finished — ${event.messages.length} messages]\n`);
          break;
      }
    };

    // Test with a prompt that triggers a tool call
    await agent.prompt("Read the package.json file", onEvent);

    console.log("Final state:");
    console.log("  isStreaming:", agent.state.isStreaming);
    console.log("  messages:", agent.state.messages.length);
    process.exit(0);
  } catch (error) {
    const message = error instanceof Error ? error.message : String(error);
    console.error(`Error: ${message}`);
    process.exit(1);
  }
}

main();
```
